SenseVoice 语音指令集成说明
==========================

适用目标
--------
本说明用于把当前仓库里的 `mic_test.py` 相关能力，集成到另一个由 `TypeScript + Python` 开发的 AI agent 中，作为“语音指令输入”模块。

目标不是直接把当前 demo 原样复制进去，而是把其中可复用的能力拆出来，接入你的 agent 主流程。


一、先明确集成目标
------------------
建议把最终链路拆成 4 段：

1. 热键或按钮触发录音
2. 采集短语音音频
3. 调用 SenseVoice 做语音识别
4. 把识别文本送入 AI agent 的任务理解与执行链路

推荐的数据流：

  用户说话
  -> 音频采集
  -> ASR 识别
  -> 文本标准化
  -> Agent 意图识别 / 参数提取
  -> 执行动作

注意：
- `语音识别` 和 `Agent 理解` 最好分层处理
- 不要把“录音控制、语音识别、任务调度、动作执行”全部写进一个脚本


二、当前 demo 中哪些部分可复用
------------------------------
当前 [mic_test.py](file:///c:/Users/Administrator/Desktop/python_test/SenseVoice-main/mic_test.py) 里，真正有复用价值的核心有两部分：

1. 模型加载
- 使用 `AutoModel(...)` 加载 `SenseVoiceSmall`
- 使用 `remote_code="./model.py"`
- 使用 `device="cuda:0"` 或 `cpu`

2. 音频识别
- 输入一段短音频
- 调用 `model.generate(...)`
- 通过 `rich_transcription_postprocess(...)` 得到最终文本

当前 demo 中“不建议原样直接搬进 agent 主系统”的部分：

1. 热键监听
- 现在用的是 `pynput` + `Ctrl+Z`
- 这更像一个本地桌面 demo 交互方式

2. 终端打印
- 现在输出是面向人工调试的日志
- 真正集成时应该返回结构化结果，而不是只 `print`

3. 临时文件路径和循环逻辑
- 现在是 demo 级写法
- 集成时最好抽成独立服务或模块


三、推荐的系统分工
------------------
对于 `TypeScript + Python` AI agent，建议采用下面的职责划分。

TypeScript 侧负责：
- UI 或桌面快捷键
- 麦克风开始/停止控制
- 录音状态展示
- 与 Python ASR 服务通信
- 把识别文本送入 agent 主流程

Python 侧负责：
- 加载 SenseVoice 模型
- 执行音频识别
- 返回结构化识别结果
- 管理 GPU 资源

不建议让 TypeScript 直接承担模型推理，也不建议让 Python 继续负责桌面热键和完整 UI。


四、推荐的集成架构
------------------
推荐优先级如下。

方案 A：Python 常驻 ASR 服务 + TypeScript 调用
-------------------------------------------
这是最推荐的方式。

基本思路：
- Python 进程启动一次
- 启动时加载模型
- 对外暴露一个本地接口
- TypeScript 把录到的音频发给 Python
- Python 返回识别文本

优点：
- 模型只加载一次，延迟低
- TypeScript 和 Python 边界清晰
- 后续容易扩展到 HTTP / WebSocket / gRPC
- 最适合集成到长期运行的 agent

推荐接口形式：
- 本地 HTTP API
- 本地 WebSocket

最简单可落地的接口：
- `POST /asr/transcribe`
- 输入：wav 文件或字节流
- 输出：JSON 结果


方案 B：TypeScript 每次调用 Python 子进程
---------------------------------------
基本思路：
- TypeScript 每次录完音后，执行一次 `python xxx.py input.wav`
- Python 输出文本
- TypeScript 读取 stdout

优点：
- 开发简单
- 适合最小验证

缺点：
- 每次调用都可能重新加载模型
- 延迟高
- 进程管理麻烦
- 不适合正式 agent 场景

结论：
- 只适合 POC
- 不建议用于正式长期运行的语音指令入口


五、建议的模块拆分
------------------
建议把当前 demo 拆成下面几个 Python 模块。

1. `asr_service.py`
- 负责加载模型
- 提供识别函数
- 提供本地服务接口

2. `asr_core.py`
- 封装 `load_model()`
- 封装 `transcribe_audio(...)`
- 与 CLI、服务层解耦

3. `mic_test.py`
- 保留为本地调试工具
- 不作为正式集成入口

推荐的 Python 核心函数形态：

  load_model(device: str) -> model
  transcribe_file(model, wav_path: str, language: str) -> dict
  transcribe_bytes(model, audio_bytes: bytes, language: str) -> dict

返回结果建议统一为结构化 JSON：

  {
    "success": true,
    "text": "打开项目并运行测试",
    "language": "zh",
    "duration_ms": 3200,
    "inference_ms": 180,
    "source": "microphone"
  }


六、TypeScript 侧建议怎么接
--------------------------
TypeScript 侧建议不要直接复用 `mic_test.py` 的热键监听逻辑，而是只负责“录音 + 发请求 + 收结果”。

推荐职责：
- 监听热键或 UI 按钮
- 录制 PCM/WAV
- 上传给 Python ASR 服务
- 拿到文字后调用 agent

推荐在 TypeScript 侧保留的状态：
- `idle`
- `recording`
- `transcribing`
- `dispatching`
- `error`

这样用户可以清楚看到当前是在：
- 等待说话
- 正在录音
- 正在识别
- 正在给 agent 下发任务


七、音频格式建议
----------------
为了减少兼容性问题，建议 TypeScript 发给 Python 的音频统一成：

- 单声道
- 16k 采样率
- PCM WAV
- 时长尽量控制在 10 秒以内

理由：
- 这和当前 demo 逻辑最接近
- 最利于短指令识别
- 便于控制请求体大小

如果 TypeScript 侧录出来不是这个格式，建议在上传前做一次标准化转换。


八、模型服务设计建议
--------------------
建议 Python 侧的 ASR 服务具备以下特性。

1. 启动时预加载模型
- 避免每次请求重新初始化

2. 单例模型实例
- 同一进程内只保留一个模型对象

3. 请求级超时
- 避免某次识别卡死

4. 错误捕获
- 任何异常都返回结构化错误

5. 健康检查接口
- 例如 `GET /health`
- 用于让 TypeScript 判断 Python 服务是否可用

建议的最小接口：

1. `GET /health`
返回：

  {
    "ok": true,
    "model_loaded": true,
    "device": "cuda:0"
  }

2. `POST /asr/transcribe`
返回：

  {
    "success": true,
    "text": "打开浏览器并搜索今天的天气"
  }


九、Agent 集成时要考虑的关键技术点
--------------------------------
1. 不要把 ASR 文本直接当成最终执行命令
- 识别文本可能有错字、口语、省略信息
- 建议加一层“命令理解”或“意图归一化”

例如：
- 原始 ASR：`帮我打开项目然后跑下测试`
- 标准化后：`打开项目，并执行测试`
- 再转成 agent 内部任务结构


2. 加一层命令确认策略
- 高风险操作不要直接执行
- 特别是文件删除、远程发布、付款、批量修改等动作

推荐策略：
- 低风险指令：直接执行
- 中风险指令：简短确认
- 高风险指令：强制二次确认


3. 处理误触发
- 热键可能误按
- 环境噪音可能触发无效输入

建议加规则：
- 空文本直接丢弃
- 少于一定字符数且置信度低时丢弃
- 连续重复的同一句话做去重


4. 控制识别时长
- 你的场景是短指令
- 不建议让一次录音无限长

建议：
- 3 到 8 秒最合适
- 最长不超过 10 到 15 秒


5. 做好语言策略
- 如果你的 agent 主要是中文指令，建议固定 `language="zh"`
- 不建议默认 `auto`，除非确实需要中英混合


6. 明确同步与异步边界
- 录音是前端交互行为
- 识别是后端推理行为
- Agent 执行可能是更长时间的异步任务

建议在 TypeScript 侧分开处理：
- 录音完成 -> 发识别请求
- 识别成功 -> 提交 agent
- agent 返回 -> 更新 UI


7. 记录日志但避免泄露隐私
- 语音命令可能包含隐私内容
- 不建议默认长期保留原始音频

推荐默认策略：
- 默认不保留原始音频
- 默认只保留必要文本日志
- 高敏场景支持完全不落盘


十、关于热键的建议
------------------
当前 demo 使用 `Ctrl+Z` 作为录音键，这只适合本地桌面调试。

真正集成到 AI agent 时，更推荐以下方式之一：

1. UI 按钮
- 按住说话
- 松开结束

2. TypeScript 侧全局热键
- 在 Electron 或桌面容器里管理

3. Web 场景下浏览器录音按钮
- 让浏览器负责麦克风权限和录音

不建议让 Python 服务继续负责热键监听，因为这会让它和桌面环境强耦合。


十一、关于临时文件与内存传输
----------------------------
当前 demo 是：
- 先保存临时 wav
- 再把路径传给模型

正式集成时有两种选择。

方案 1：继续使用临时文件
- 开发最简单
- 易于调试

方案 2：直接内存字节传输
- 更干净
- 少一次磁盘 IO
- 更适合服务化

建议：
- 第一版可以先用临时文件
- 稳定后再改成字节流或内存数组


十二、关于并发
--------------
如果你的 agent 只允许一个语音输入会话同时进行，最简单。

如果未来要支持：
- 多用户
- 多会话
- 并发识别

则要额外考虑：
- Python 服务的并发模型
- GPU 资源复用
- 请求排队
- 超时取消

第一阶段建议：
- 单模型单实例
- 单请求串行处理
- 把功能先跑稳


十三、建议的落地顺序
--------------------
建议按下面顺序推进。

第一步：抽出 Python 核心识别函数
- 把 `mic_test.py` 中的模型加载和识别逻辑抽成可复用函数

第二步：做 Python 本地 ASR 服务
- 提供 `health` 和 `transcribe` 接口

第三步：TypeScript 接音频录制
- 录完音后发给 Python 服务

第四步：把识别文本接到 agent
- 先只打印文本
- 再接任务理解
- 最后再接实际执行

第五步：补充保护机制
- 超时
- 错误提示
- 风险确认
- 日志


十四、最低可用集成方案
----------------------
如果你现在想最快接进去，建议直接做这个最小版本：

1. TypeScript 录音得到 `wav`
2. TypeScript 调 Python 本地 HTTP 服务
3. Python 返回：

  {
    "success": true,
    "text": "打开当前项目并运行测试"
  }

4. TypeScript 拿到 `text` 后，调用现有 agent 的文本入口

这套方式最容易和现有 agent 结构对齐。


十五、最终建议
--------------
结论很明确：

1. `mic_test.py` 适合作为 demo 和本地调试工具
2. 正式集成时不要把它原样塞进 agent
3. 应该把它拆成：
- TypeScript 负责交互和录音
- Python 负责 ASR 推理
- Agent 负责文本理解和动作执行

如果按这个边界来做，后续你要替换模型、加 VAD、加热词、加命令确认、加多轮对话，都会容易很多。
