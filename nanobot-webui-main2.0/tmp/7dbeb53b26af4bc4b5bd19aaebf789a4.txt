How to rebuild object definitions that are stored in the data dictionary  \n\nYou want to rebuild PL/SQL(packages, procedures, functions or triggers), grants, indexes, constraints or storage clauses(old table structure) with DUL. This can be done but is a little bit tricky. You need to unload the relevant data dictionary tables using DUL and then load these tables into a healthy database, be sure to use a different user than sys or (system). Loading the data dictionary tables of the crashed database into the healthy database dictionary could corrupt the healthy database as well.  \n\nDetailed explanation to retrieve for example pl/sql packages / procedures / functions from a corrupted database :  \n\n1) Follow the steps explained in the \"Using DUL\" section and unload the data dictionary table \"source\\$\"   \n2) Create a new user into a healthy database and specify the desired default and temporary tablespace.   \n3) Grant connect, resource, imp_full_database to the new user.   \n4) Import/load the table \"source\\$\" into the new created schema: e.g.: imp80 userid $=\\&\\mathtt{1t}$ ;username>/&lt;password> file $=$ &lt;path>\\&lt;name>.dmp log $=0$ :\\&lt;path>\\&lt;name>.txt full=y  \n\n5) You can now query from the table &lt;newuser.source\\$> to rebuild the pl/sql https://mosemp.us.oracle.com/epmos/faces/DocumentDisplay?_adf.ctrl-state $=$ pgrzjuemx_1372&id=72554.1  \n\nprocedures/functions from the corrupted database. Scripts can be found on WebIv to generate such PL/SQL creation scripts.  \n\nThe same steps can be followed to recreate indexes, constraints, and storage parameters or to regrant privileges to the appropiate users. Please notice that you always need to use a script of some kind that can recreate the objects and include all the features of the crashed database version. For example : when the crashed database is of version 7.3.4 and you have several bitmap indexes, if you would use a script that supports version 7.3.2 or prior, then you won't be able to recreate the bitmap indexes succesful !  \n\n4. How to unload data when the segment header block is corrupted  \n\nWhen DUL can't retrieve data block information on the normal way, it can scan the database to create its own segment/extent map. The procedure of scanning the database is necessary to unload the data from the datafiles. (to illustrate this example I copied an empty block ontop of the segment header block)  \n\n1) Create an appropiate \"init.dul\" (see 2.1) and \"control.dul\" (see 2.2) file.  \n\n2) Unload the table. Below is a structured overview of its key use cases, commands, and considerations:\n\n---\n\n### **1. Basic Setup for DUL**\n- **`init.dul`**: Defines the database instance (e.g., `db_name`, `db_block_size`).\n- **`control.dul`**: Specifies datafiles to recover (e.g., `datafile 1 \"D:\\path\\file.dbf\"`).\n- **Note**: Avoid including the **system tablespace** if it's corrupted or unavailable.\n\n---\n\n### **2. Recovery Scenarios and Commands**\n\n#### **A. Corrupted Segment Header (e.g., `ORA-01578`)**\n- **Symptoms**: Query failures, \"Could not read/parse segment header.\"\n- **Steps**:\n  1. Use `scan database` to build an extent map.\n  2. Set `alter session set use_scanned_extent_map = true;` to bypass corrupted segment headers.\n  3. Run `unload table` to extract data.\n\n**Example**:\n```sql\nDUL> scan database; -- Builds extent map\nDUL> alter session set use_scanned_extent_map = true;\nDUL> unload table scott.emp; -- Unloads data using the scanned map\n```\n\n---\n\n#### **B. Corrupted Datafile Header**\n- **Symptoms**: Database mount failure (e.g., `ORA-01122`, `ORA-01251`).\n- **Approach**:\n  - DUL can recover data without the corrupted datafile header.\n  - Alternative: Use Oracle's `DBMS_RECOVER` or patch the header (not covered here).\n\n---\n\n#### **C. Missing System Tablespace**\n- **Impact**: Loss of metadata (e.g., `USER$`, `OBJ$`, `TAB$`, `COL$`), making table/column names unknown.\n- **Workaround**:\n  1. Use **old system tablespace backups** from the same database.\n  2. If unavailable:\n     - Use `scan database` and `scan tables` to identify data.\n     - Tables are named `T_O<oid>` (e.g., `T_O1078`), with columns labeled `C1`, `C2`, etc.\n     - Guess column types based on data (e.g., `NUMBER`, `VARCHAR2`).\n\n**Example Output**:\n```sql\nUNLOAD TABLE T_O1078 (C1 NUMBER, C2 UNKNOWN, C3 UNKNOWN) STORAGE (TABNO 0 EXTENTS( FILE 6 BLOCK 2));\n```\n\n---\n\n#### **D. Recovering Data Without Metadata**\n- **Steps**:\n  1. Run `scan database` and `scan tables` to build extent/segment maps.\n  2. Use `unload table` with guessed column definitions.\n  3. Redirect output to a log file for large datasets:\n     ```bash\n     C:\\> dul8 > c:\\output\\scan_tables.txt scan tables; exit;\n     ```\n\n---\n\n### **3. Key DUL Commands**\n- `scan database`: Builds extent/segment maps.\n- `alter session set use_scanned_extent_map = true;`: Bypasses corrupted headers.\n- `unload table <table_name>`: Extracts data (requires metadata or guessed schema).\n- `scan tables`: Identifies tables and their storage details.\n\n---\n\n### **4. Limitations and Considerations**\n- **Metadata Loss**: Without the system tablespace, table/column names are unknown. Requires deep RDBMS knowledge.\n- **Data Types**: DUL may not accurately guess column types (e.g., `UNKNOWN`).\n- **Manual Effort**: Identifying tables and columns from raw data (e.g., `T_O1078`) is time-consuming.\n- **Backup Importance**: Always maintain backups of the system tablespace for critical recovery.\n\n---\n\n### **5. Best Practices**\n- **Preventive Measures**:\n  - Regularly back up the system tablespace.\n  - Test DUL on non-critical databases to understand its behavior.\n- **Post-Recovery**:\n  - Validate data integrity after extraction.\n  - Rebuild metadata if possible using Oracle tools.\n\n---\n\n### **6. Example Recovery Workflow**\n1. Create `init.dul` and `control.dul` files.\n2. Run `scan database` to map extents.\n3. Use `alter session` to bypass corrupted headers.\n4. Identify tables via `scan tables` output.\n5. Unload data with `unload table` and guessed schemas.\n\n---\n\n**Note**: DUL is a low-level tool requiring advanced knowledge of Oracle internals.
