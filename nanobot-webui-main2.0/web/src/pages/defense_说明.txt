Defense 页面开发说明
======================

一、背景
--------
本次开发的目标，是让 WebUI 可以维护危险命令策略文件
`runtime/tool_policy.json`，并让该策略在 agent 的 tool 执行前真正生效。

核心目标分为两部分：

1. 在 WebUI 页面上维护危险命令策略
2. 在后端执行 tool call 之前，根据策略做 block 或 warn


二、本次实现内容
----------------

1. Defense 页面从静态演示页，改为真实可维护策略文件的页面
   - 页面现在会通过后端 API 读取启动参数 `--tool-policy` 指向的策略文件
   - 当前正式启动脚本使用 `runtime/tool_policy.json`
   - 支持新增、编辑、删除规则
   - 支持保存回 JSON 文件

2. 新增启动参数 `--tool-policy`
   - WebUI 启动时可通过该参数传入策略文件路径
   - 例如：
     `--tool-policy E:\nanobot-main\nanobot-webui-main2.0\runtime\tool_policy.json`

3. 新增后端策略读写服务
   - WebUI 后端增加了 tool policy 的服务和 API
   - 页面保存后会直接写回 JSON 文件

4. 危险命令策略支持两种匹配方式
   - `literal`
   - `regex`

5. 危险命令策略真正接入 agent tool 执行链路
   - 在 tool 真正执行前拦截
   - `mode=block` 时直接拒绝执行
   - `mode=warn` 时暂停执行，等待用户授权

6. 用户提示信息统一改为英文
   - 包括 block、warn、等待授权、取消执行等提示


三、tool_policy.json 结构
-----------------------------------

当前每条规则主要字段如下：

- `command`
  - 规则内容
  - 当 `matchType=literal` 时，表示普通关键字
  - 当 `matchType=regex` 时，表示 Python `re` 正则表达式

- `matchType`
  - `literal` 或 `regex`

- `regexFlags`
  - 当前支持：
    - `i`：忽略大小写
    - `m`：多行模式
    - `s`：dot 匹配换行

- `category`
  - 规则分类，例如 `oracle`、`filesystem`、`linux`

- `severity`
  - 风险级别，例如 `high`、`critical`

- `mode`
  - 处理方式：
    - `block`
    - `warn`

- `scope`
  - 规则作用范围，例如 `SQL`、`Shell`

- `note`
  - 规则说明


四、literal 与 regex 的区别
----------------------------

1. `literal`
   - 适合简单关键字匹配，例如：
     - `drop table`
     - `delete from`
     - `rm -rf`
   - 当前后端会自动做：
     - 大小写不敏感匹配
     - 多个连续空格压缩
   - 所以：
     - `drop table`
     - `DROP TABLE`
     - `drop     table`
     都可以识别

2. `regex`
   - 适合复杂规则
   - 当前按 Python `re` 语法处理
   - 例如检测“update 但没有 where”的规则：

     `\bupdate\b[\s\S]*?\bset\b(?:(?!\bwhere\b)[\s\S])*$`

   - 在 JSON 中需要写成转义后的形式：

     `\\bupdate\\b[\\s\\S]*?\\bset\\b(?:(?!\\bwhere\\b)[\\s\\S])*$`


五、Defense 页面支持的能力
--------------------------

当前页面支持：

1. 查看当前策略文件路径和更新时间
2. 查看规则列表
3. 搜索规则
4. 编辑规则字段
5. 选择匹配方式 `literal / regex`
6. 编辑 `regexFlags`
7. 保存策略到 JSON 文件
8. 页面上查看 regex 使用说明


六、后端执行拦截逻辑
--------------------

危险命令策略不仅用于页面展示，还已经真正接入 agent 的 tool 执行流程。

逻辑如下：

1. 当模型生成 tool call 后
2. 在 tool 真正执行之前，系统会读取策略
3. 如果命中规则：
   - `block`
     - 直接拒绝执行
     - 返回英文提示，说明该 tool call 已被拦截
   - `warn`
     - 暂停执行
     - 记录待授权状态
     - 等待用户明确回复批准或取消

当前授权文本支持中英双语，例如：

- 批准：
  - `approve`
  - `同意执行`
  - `批准执行`

- 拒绝：
  - `cancel`
  - `拒绝`
  - `取消`

--------------------

当前默认策略中，已经包含如下典型规则：

十、结论
--------

本次开发已经完成两件关键事情：

1. `Defense` 页面可以真实维护启动参数指定的 `tool_policy.json`
2. 策略已经真正进入 agent 的 tool 执行链路，可以对危险命令做 block 或 warn

这意味着：

- 页面维护的规则，不再只是展示
- 修改 JSON 后，可以真正影响危险命令的执行行为


十一、main3 兼容层回归案例：规则存在但未拦截
----------------------------------------------

### 1. 故障现象

Defense 页面和 `runtime/tool_policy.json` 中均存在：

`truncate table -> literal -> block`

但 Agent 仍通过 SQLCL MCP 工具执行了：

`truncate table VALEN.TEST1;`

### 2. 排查结论

规则内容、大小写归一化、SQLCL 工具参数均没有问题。使用实际参数直接调用
`DangerousToolPolicy.evaluate()` 时，可以正确得到 `action=block`。

真正的问题发生在 WebUI 启动顺序中：

1. `webui.__main__` 首先执行 `webui.patches.apply_all()`
2. `mcp_dynamic.py` 和 `subagent.py` 都会包装 `AgentLoop.__init__`
3. 旧包装函数没有使用 `functools.wraps`，运行时签名退化为 `(self, *args, **kwargs)`
4. `_agentloop_supports_init_kwarg()` 只查找显式的 `hook_factories` 参数
5. 能力检测错误返回 `False`
6. `LegacyToolPolicyHook` 没有注册到 main3 的 turn hook 链
7. MCP 工具因此绕过策略并直接执行

注意：Defense 页面只负责读取和保存策略。真正的安全边界位于
`LegacyToolPolicyHook.before_execute_tool()`；页面显示有规则并不能证明运行中的 Agent
已经安装该 Hook。

### 3. 修复方式

本项目同时采用两层修复：

1. 所有包装 `AgentLoop.__init__` 的 monkey patch 使用 `functools.wraps`，保留原始签名和
   `__wrapped__` 链。
2. `_agentloop_supports_init_kwarg()` 除了识别显式参数，也把 `**kwargs`
   （`inspect.Parameter.VAR_KEYWORD`）视为支持该关键字，防止未来新增包装器时再次静默关闭安全 Hook。

不要只做其中一层：保留签名方便调试和反射，`**kwargs` 兜底则负责兼容未来补丁。

### 4. 回归测试

`tests/agent/test_tool_policy_guard.py` 必须覆盖以下三点：

1. 按真实 WebUI 导入顺序应用所有 monkey patch 后，`AgentLoop.__init__` 仍能识别
   `hook_factories`。
2. 仅暴露 `**kwargs` 的未来包装器不会让能力检测返回 `False`。
3. 工具名为 `mcp_oracle-sqlcl_run-sql`，参数包含
   `{"sql": "truncate table VALEN.TEST1;"}` 时，Hook 在工具执行前抛出 block 异常。

修改 AgentLoop 构造函数、WebUI patch 顺序、Hook 工厂或 SQLCL MCP 适配时，都应运行：

`python -m pytest -q tests/agent/test_tool_policy_guard.py`

同时建议运行相关 main3 兼容测试：

`python -m pytest -q tests/test_webui_cron_delivery.py tests/test_subagent_patch_websocket.py`

### 5. 部署注意事项

策略 Hook 在 AgentLoop 创建时注册。修改 Python 代码后必须重启 WebUI；仅刷新浏览器不会让
已经运行的 AgentLoop 获得新 Hook。策略 JSON 本身支持按文件修改时间重新加载，无需为每次
规则编辑重启服务。
