# Oracle Vector Search 数据结构说明

本文档说明当前 FastAPI Demo 使用的 Oracle 表结构设计、字段含义、约束规则以及典型查询关系。

相关文件：

- 表结构 SQL：
  - `oracle_vector_schema.sql`
- API 服务：
  - `oracle_vector_api.py`
- LangChain Demo：
  - `oracle_langchain_demo.py`


## 1. 设计目标

当前数据库设计用于支持以下能力：

1. 保存文档级元数据
2. 保存完整文档原文
3. 保存文档分片内容
4. 保存每个分片的向量 embedding
5. 支持 Oracle 向量检索
6. 支持按文档聚合检索结果
7. 避免重复上传同名文档


## 2. 表清单

当前使用两张主表：

1. `LC_DEMO_DOCUMENTS`
2. `LC_DEMO_CHUNKS`

说明：

- `LC_DEMO_DOCUMENTS` 保存文档级数据
- `LC_DEMO_CHUNKS` 保存分片级数据

之所以拆成两张表，是因为业务要求同时存在：

- 文档名唯一
- 一个文档可以拆成多个 chunk

如果只用一张表，则 `document_name` 唯一约束会与“同一文档多分片”冲突，因此采用主从表设计。


## 3. 表关系

关系如下：

- 一条 `LC_DEMO_DOCUMENTS` 记录
- 对应多条 `LC_DEMO_CHUNKS` 记录

关联字段：

- `LC_DEMO_DOCUMENTS.doc_id`
- `LC_DEMO_CHUNKS.doc_id`

约束关系：

- `LC_DEMO_CHUNKS.doc_id` 外键引用 `LC_DEMO_DOCUMENTS.doc_id`
- 删除主表记录时，分片表记录会级联删除


## 4. 文档主表

### 4.1 表名

- `LC_DEMO_DOCUMENTS`


### 4.2 用途

用于存储一份文档的“完整信息”，每个文档只保留一条记录。


### 4.3 DDL

```sql
CREATE TABLE lc_demo_documents (
    doc_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_name VARCHAR2(512) NOT NULL,
    document_text CLOB NOT NULL,
    document_type VARCHAR2(128) NOT NULL,
    source_file VARCHAR2(128),
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT uk_lc_demo_documents_name UNIQUE (document_name)
);
```


### 4.4 字段说明

| 字段名 | 类型 | 是否为空 | 说明 |
|---|---|---|---|
| `doc_id` | `NUMBER` | 否 | 文档主键，自增 |
| `document_name` | `VARCHAR2(512)` | 否 | 文档全名，如 `xxx.pdf`、`xxx.txt` |
| `document_text` | `CLOB` | 否 | 文档完整原文，不是分片内容 |
| `document_type` | `VARCHAR2(128)` | 否 | 文档类型，例如 `pdf`、`txt` |
| `source_file` | `VARCHAR2(128)` | 是 | 文档来源标识，例如 `blog` |
| `created_at` | `TIMESTAMP` | 否 | 入库时间，默认 `SYSTIMESTAMP` |


### 4.5 约束说明

#### 主键

- `doc_id`

作用：

- 唯一标识一份文档
- 用于和分片表关联


#### 唯一约束

- `uk_lc_demo_documents_name UNIQUE (document_name)`

作用：

- 防止同名文档重复入库

当前业务逻辑：

- 上传时先插入主表
- 如果触发唯一约束，则捕获异常
- 返回 `inserted = false`
- 不重复写入分片数据


### 4.6 字段使用规则

#### `document_name`

- 用作文档唯一业务标识
- 当前系统默认按文件名去重

注意：

- 如果文件名相同但内容不同，系统仍会视为同一文档
- 如果需要按内容重新入库，建议更换文件名，或先删除旧记录


#### `document_text`

- 保存文档解析后的完整文本
- PDF 文档保存“解析后的全文 txt”
- TXT 文档保存“文件原始全文”

作用：

- 支持 `return_mode = full`
- 支持后续做全文摘要、全文展示或二次分析


#### `document_type`

当前建议取值：

- `pdf`
- `txt`

作用：

- 检索时可按类型过滤
- 便于后续扩展不同解析策略


#### `source_file`

示例值：

- `blog`
- `oracle_doc`
- `manual`

作用：

- 标记文档来源
- 便于后续做分组、过滤、统计


## 5. 分片表

### 5.1 表名

- `LC_DEMO_CHUNKS`


### 5.2 用途

用于保存每个文档切分后的 chunk，以及每个 chunk 对应的向量。


### 5.3 DDL

```sql
CREATE TABLE lc_demo_chunks (
    doc_id NUMBER NOT NULL,
    chunk_id NUMBER NOT NULL,
    chunk_tokens NUMBER NOT NULL,
    chunk_text CLOB NOT NULL,
    embedding VECTOR(2048, FLOAT32) NOT NULL,
    document_type VARCHAR2(128) NOT NULL,
    source_file VARCHAR2(128),
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT pk_lc_demo_chunks PRIMARY KEY (doc_id, chunk_id),
    CONSTRAINT fk_lc_demo_chunks_doc
        FOREIGN KEY (doc_id)
        REFERENCES lc_demo_documents (doc_id)
        ON DELETE CASCADE,
    CONSTRAINT ck_lc_demo_chunks_source
        CHECK ((chunk_id = 1 AND source_file IS NOT NULL) OR (chunk_id > 1 AND source_file IS NULL))
);
```


### 5.4 字段说明

| 字段名 | 类型 | 是否为空 | 说明 |
|---|---|---|---|
| `doc_id` | `NUMBER` | 否 | 关联文档主表的主键 |
| `chunk_id` | `NUMBER` | 否 | 分片编号，从 `1` 开始顺序递增 |
| `chunk_tokens` | `NUMBER` | 否 | 当前 chunk 的 token 数 |
| `chunk_text` | `CLOB` | 否 | 当前分片文本内容 |
| `embedding` | `VECTOR(2048, FLOAT32)` | 否 | 当前分片向量 |
| `document_type` | `VARCHAR2(128)` | 否 | 文档类型，如 `pdf`、`txt` |
| `source_file` | `VARCHAR2(128)` | 是 | 只在 `chunk_id = 1` 时存储来源 |
| `created_at` | `TIMESTAMP` | 否 | 入库时间，默认 `SYSTIMESTAMP` |


### 5.5 约束说明

#### 主键

- `pk_lc_demo_chunks PRIMARY KEY (doc_id, chunk_id)`

作用：

- 确保一个文档内每个 chunk 只出现一次
- 同一文档的 `chunk_id` 不可重复


#### 外键

- `fk_lc_demo_chunks_doc FOREIGN KEY (doc_id) REFERENCES lc_demo_documents(doc_id) ON DELETE CASCADE`

作用：

- 保证分片记录必须隶属于某个已存在文档
- 删除文档时，自动删除所有相关 chunk


#### 检查约束

- `ck_lc_demo_chunks_source`

规则：

- `chunk_id = 1` 时，`source_file` 必须有值
- `chunk_id > 1` 时，`source_file` 必须为空

作用：

- 满足你的业务要求：
  - 文档源文件 `blog`
  - 只存储在分片 `chunk_id = 1`


### 5.6 embedding 字段说明

`embedding` 使用 Oracle 原生向量类型：

```sql
VECTOR(2048, FLOAT32)
```

含义：

- 向量维度：`2048`
- 单元素类型：`FLOAT32`

对应当前模型：

- `Qwen3-VL-Embedding-2B`

注意：

- 如果后续切换 embedding 维度，例如不是 `2048`
- 则必须同步修改表结构和写库逻辑


## 6. 索引设计

当前额外索引：

```sql
CREATE INDEX lc_demo_chunks_doc_type_ix
    ON lc_demo_chunks (document_type);
```

作用：

- 支持按 `document_type` 过滤检索
- 提高类型筛选下的查询效率


## 7. 数据写入规则

### 7.1 文档写入

每上传一个文件：

1. 先解析全文
2. 将全文写入 `LC_DEMO_DOCUMENTS.document_text`
3. 生成一个 `doc_id`
4. 再批量写入该文档的 chunk


### 7.2 分片写入

分片编号规则：

- 从 `1` 开始
- 按切分顺序递增

分片来源规则：

- `chunk_id = 1` 时写 `source_file`
- 其他 chunk 不写 `source_file`


### 7.3 重复写入

如果同名文档再次上传：

- 主表会命中唯一约束
- 服务会捕获异常
- 本次上传不再重复插入

返回效果：

- `inserted = false`
- `inserted_chunk_count = 0`


## 8. 数据查询规则

### 8.1 向量检索对象

实际做向量检索的是：

- `LC_DEMO_CHUNKS.embedding`

不是对完整文档直接做向量检索。


### 8.2 检索流程

流程如下：

1. 将用户 prompt 转成 query embedding
2. 在 `LC_DEMO_CHUNKS` 上做 Oracle vector search
3. 召回若干 chunk
4. 对召回 chunk 做 reranker 打分
5. 按文档聚合
6. 根据 `return_mode` 决定返回内容


### 8.3 `full` 模式的数据来源

返回内容：

- `document_name`
- `document_text`

数据来自：

- `LC_DEMO_DOCUMENTS`


### 8.4 `split` 模式的数据来源

返回内容：

- `document_name`
- 命中且达分数阈值的多个 `chunk_text`

数据来自：

- `LC_DEMO_DOCUMENTS`
- `LC_DEMO_CHUNKS`


### 8.5 `title` 模式的数据来源

返回内容：

- `document_name`

数据来自：

- `LC_DEMO_DOCUMENTS`


## 9. 典型查询关系

### 9.1 查询一个文档及其所有分片

```sql
SELECT d.doc_id,
       d.document_name,
       d.document_type,
       c.chunk_id,
       c.chunk_tokens,
       c.chunk_text
  FROM lc_demo_documents d
  JOIN lc_demo_chunks c
    ON d.doc_id = c.doc_id
 WHERE d.document_name = :document_name
 ORDER BY c.chunk_id;
```


### 9.2 查询文档全文

```sql
SELECT doc_id,
       document_name,
       document_text
  FROM lc_demo_documents
 WHERE document_name = :document_name;
```


### 9.3 查询某类文档的 chunk 数量

```sql
SELECT document_type,
       COUNT(*) AS chunk_count
  FROM lc_demo_chunks
 GROUP BY document_type;
```


## 10. 示例数据语义

以一个 PDF 文档为例：

- `LC_DEMO_DOCUMENTS` 中只有 1 条记录
- `LC_DEMO_CHUNKS` 中会有多条记录
- 假设被切成 6 个 chunk，则：
  - `chunk_id` 为 `1` 到 `6`
  - `source_file` 仅 `chunk_id = 1` 有值
  - 每条 chunk 都有独立的 `embedding`


## 11. 当前限制

当前结构适合 Demo 和中小规模验证，但有以下限制：

1. 文档去重基于文件名，不基于内容哈希
2. 目前没有单独保存标题、摘要、作者等文档元数据
3. 目前没有分区策略
4. 目前未单独增加 ANN 向量索引说明
5. embedding 维度当前写死为 `2048`


## 12. 后续可扩展方向

如果后面要做成正式系统，建议考虑增加：

1. 文档内容哈希字段
2. 文档更新时间字段
3. 文档状态字段
4. 向量索引策略
5. 多租户字段
6. 业务标签字段
7. 文档权限控制字段


## 13. 结论

当前这套表结构的核心特点是：

- 文档和分片分离
- 完整原文和分片文本同时保存
- Oracle 原生向量字段存 embedding
- 文档名唯一，避免重复上传
- 兼容 `full`、`split`、`title` 三种返回模式

对于当前 Demo 和系统接入阶段，这个设计已经足够清晰、稳定，且便于后续扩展。
